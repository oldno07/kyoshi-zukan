## 1. 修正：「既存デザインをできるだけ維持」を撤回する

### 元の指示（問題箇所）

> 現在のUIをできるだけ維持してください。デザイン変更ではなく、内部構造を改善してください。

### 修正方針

**維持するもの**と**作り直すもの**を分離する。「デザイン」と「情報設計」は別物であり、後者は今回のリニューアルで必ず手を入れる。

| 分類                 | 対象                                                                        | 方針                                                         |
| -------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 維持する（意匠）     | SCP財団風UI言語（ステータスバー、リティクル演出、じと目・口なしの絵づくり） | そのまま踏襲。図鑑の「研究ログの温度」を担う核なので変更不要 |
| 作り直す（情報設計） | 1ページ内の情報配置順序・重複表示                                           | 下記2章の通り再設計する                                      |

### 現行サイトで確認済みの具体的な欠陥（再掲・実データ確認済み）

現行 `entry.html` は、`TYPE`（系統）の値がヒーロー部・ステータス表・ページ下部のSYSディバイダーの**3箇所に同一の値でそのまま重複表示**されている。`HABITAT`も同様。これが「図鑑を読む体験」ではなく「データベース照会画面」に見える直接の原因である。Astroへ内部構造だけ移しても、同じHTML構造をコピーすれば同じ問題がそのまま残る。

## 2. 情報設計の再設計方針

1ページの情報を「起（識別）→承（生態・行動）→転（現在の観測状況・余韻）」の順に一本化し、同じ値を複数箇所で繰り返さない。

- ヒーロー部：個体名・レアリティ・系統タグのみ（識別情報の一発表示）
- ステータス表：数値系（植物性／動物性／危険度）に限定。文字列項目（HABITAT・TYPE等）はヒーロー部と重複させない
- 本文（desc）：総則第2部2-7節の文章表現ルール（体言止め書き出し／漢字は開く／断定を避ける／一文一情報／3段落構成）をそのままAstroのMarkdown本文として運用する
- ページ下部の反復表示（SYSディバイダー）は廃止、または「関連生物」「タグ」など**まだ出していない情報**に差し替える

## 8. 実装ルール（保守性・データ整合性）

### 8-1. Single Source of Truth

同じ情報は必ず一箇所だけに保持する。表示の都合で同じ値を複数箇所へ保存・定義してはならない。

例：TYPE／HABITAT／STATUS／タグ／シリーズ

これらはFrontmatter（一次情報）のみを唯一の情報源（Single Source of Truth）とする。画面ごとの表示はすべてビルド時に生成する。

> 本書1章・2章で指摘した「TYPEが1ページ内に3箇所重複表示される」現行の欠陥は、この原則を守ることで構造的に再発しなくなる。

### 8-2. 表示専用データを保存しない

画面表示のためだけの集計値は保存しない。以下は保持禁止とする。

発見数／タグ数／関連数／シリーズ数／完売件数／公開数

これらはビルド時にFrontmatterから毎回算出する。保存するのは一次情報のみとする。

> 本書4章「発見数カウンター」「完売実績の可視化」は、この原則の通りビルド時算出として設計済み。齟齬なし。

### 8-3. Astro Content Collections Schema

Content CollectionsはSchemaを必ず定義する。FrontmatterはSchemaにより型チェックを行い、ビルド時に入力ミスを検出できる構造とする。

対象：no／category／status／danger／tags／related／soldOut 等

型を固定し、誤入力を防止する。Schemaを変更した場合は既存データとの互換性も確認する。

### 8-4. メディア管理ルール（折衷版）

画像・動画は各生物フォルダ内で管理し、命名規則を統一する。

```
cover.webp
gallery01.webp
gallery02.webp
comic01.webp
comic02.webp
movie.mp4
```

画像ファイルの存在確認はフォルダ走査に任せる（新しい画像はフォルダへ追加するだけでギャラリーへ反映される）。

ただし、フォルダ走査だけでは**ギャラリー画像1枚ごとの研究員コメント（title／desc）を再現できない**。現行サイトの実データでは、ギャラリー画像に個別のキャプション（例：「植物棚での人工飼育に成功」「脱走に気をつけて飼育しています。」）が付いており、これは図鑑としての演出上省略できない。そのため、キャプションのみfrontmatter側に画像ファイル名をキーとした最小限のマッピングとして持たせる。

```yaml
gallery_captions:
  gallery01.webp:
    title: "植物棚での人工飼育に成功"
    desc: "脱走に気をつけて飼育しています。"
```

キャプションが未設定の画像は、タイトルなしでそのままギャラリーに表示する。「フォルダに置くだけで反映される」という保守性の理想は壊さない。

### 8-5. データ重複の禁止

同じ内容を複数のファイルへ記述してはならない。

例：Creature名をNewsへ再入力する／Creature情報をReportsへコピーする／タグ名を複数箇所へ定義する

必要な場合はslugやIDによる参照のみを保持し、表示時に関連データを解決する。これにより表記ゆれ・更新漏れを防止する。

### 8-6. 設計原則

本要件書に記載されていない仕様を実装者の判断で追加・変更してはならない。

仕様変更が必要と判断した場合は、変更理由／影響範囲／代替案を提示し、承認を得てから実装すること。

利便性のみを理由に世界観・運用ルールを変更してはならない。

### 8-7. デザイン不可侵の原則

機能修正・データ構造修正のタスクにおいて、CSS（配色・フォント・余白・コンポーネントの見た目）を変更してはならない。

- 「hidden個体の伏せ字表示」「一覧のフィルターUI追加」のような機能追加であっても、**既存のCSS変数・クラス名・デザイントークンをそのまま使うこと**。新しい見た目が必要な場合も、既存のデザイン言語（配色・フォント・枠線のスタイル）から逸脱しないこと
- 機能修正のコミットに、意図しないCSSの変更が混ざっていないか、**コミット前に必ず`git diff`で`css/`・`styles/`配下の差分を確認**すること。機能と無関係なCSSの変更行が含まれていたら、それは事故なので元に戻してからコミットする
- デザインそのものを変更したい場合は、必ずそれを独立したタスクとして明示的に依頼する。機能修正のついでに「ついでにここも良くしておいた」という変更は禁止

## 9. 着手前に確認・決定が必要な事項（今回の読み直しで新たに発見）

本書0〜8章は「完成後の姿」を定義しているが、**現行データから新構造へどう移行するか**が一切書かれていない。これを決めないまま実装エージェントに渡すと、slug命名や画像変換を実装側の推測で進めてしまい、後から全件やり直しになるリスクが高い。着手前に以下を確定させる。

### 9-1. スラッグ（slug）命名規則 → 確定：`no`＋英名スラッグ

**確定：`[no]-[英名スラッグ]` 形式とする。** 例：`021-gnyacilius`（No.021 グニャキリス／英名 Gnyacilius）

生成規則：`entries.js` の `en` フィールドを小文字化し、英数字以外（スペース・記号）をハイフンに置換して連結する。番号を先頭に含めることで、和名・英名の乖離が大きい個体（No.006「キンタ魔丸」等）でも重複や表記揺れの心配がなく、番号を見れば台帳（03マスター台帳）との突合も機械的に行える。

25体＋EX＋MISSING全件分を機械生成した上で、**人間による目視レビューを1回挟む**（自動変換だけで確定させない。特に英名に長い修飾語が付く個体は不自然なスラッグになりやすいため）。

### 9-2. 既存アセットの移行・変換手順が未定義

現行は `images/no_021_01.jpg` のようなフラットな1フォルダ管理で、拡張子も `.png` `.PNG` `.jpg` `.JPG` が混在している（既報の⑦）。新構造は `cover.webp` `gallery01.webp` 等のフォルダ内命名・webp統一を前提としている。

つまり移行には**画像フォーマット変換（png/jpg → webp）と再配置・リネームを行うスクリプト**が必要だが、本書にはその作業自体がタスクとして存在しない。誰が・どの段階で・自動か手動かを決める必要がある。

### 9-3. 旧URLとの互換性（リダイレクト）→ 確定：フェーズ1の必須タスクとする

現行URLは `entry.html?no=021` 形式。新URLは `/creatures/021-gnyacilius/` 形式になる。この間の**301リダイレクトを、フェーズ1のリリース条件に含める**（ドメイン移管の判断とは切り離し、今回のAstro移行と同時に対応する）。

具体的には、Cloudflare Pagesの `_redirects` ファイルに、`entries.js` の全 `no` を走査して機械的に以下のマッピングを生成する。

```
/entry.html?no=021  /creatures/021-gnyacilius/  301
```

25体＋EX＋MISSING全件を対象とし、ビルドスクリプト側で `entries.js`（旧）→ 新frontmatterのslug対応表から自動生成すること（手作業での表作りは事故のもとなので避ける）。過去のInstagram投稿・ストーリーズ・プロフィールリンクに埋め込まれた旧URL形式からのアクセスを保護する。

> 注：`pelicanworks.site` へのドメイン移管に伴うリダイレクト（10章）は、移管先URLが未確定のため本タスクとは別枠。移管実行時に別途対応する。

## 10. URL構成変更（`pelicanworks.site/zukan`）との関係について

別スレッドで検討中の「独自ドメイン取得＋ `pelicanworks.site/zukan` に図鑑、`pelicanworks.site/labo` に研究所、トップページ廃止」という構想について、本書との関係を整理する。

- 本書0〜8章で定義した `/creatures/[slug]/` というURL設計は、**ドメイン名やサブパスに依存しない相対パス設計**である。したがって、フェーズ1〜3の開発は現行ドメイン（`kyoshi-zukan.pages.dev`）上でそのまま進めてよく、ドメイン移管の意思決定を待つ必要はない
- ドメイン移管が決まった段階で、Astroの `base` 設定（サブパス配下に配置する場合の接頭辞指定）とCloudflare Pages側のドメイン設定を追加するだけで対応できる。**作り直しにはならない**
- ただし、移管を実行する際は必ず**新旧URLの301リダイレクト表**を用意すること。対象は、①現行 `kyoshi-zukan.pages.dev` の全URL、②OGPメタタグに残っている旧canonical `oldno07.github.io/kyoshi-zukan`（本書9-3と合わせて存在が判明した、現状ですでに二重化しているドメインの片方）、③Instagramプロフィール欄・過去投稿に埋め込まれた旧リンク。これらを洗い出さないまま「トップページ廃止」を実行すると、蓄積してきたシェア資産・被リンクが一度に無効化される
- 結論：**ドメイン移管の実行判断は保留のままでよいが、その判断が下るまでの間、フェーズ1〜3の開発は止める必要がない**。両者は独立している

## 11. `WORLD`ナビゲーションと`land.html`（研究所）の関係について（確認済み・意図的仕様）

実データ確認により、ナビゲーションの`WORLD`は`about.html`（世界観・生態分類体系の解説ページ）にリンクしており、`land.html`（研究所のランディングページ、Instagram流入者向け）とは**別ページ**であることが判明した。

現行`index.html`のナビゲーションに`land.html`への導線は存在しない。これはボスに確認済みの通り、**意図的な設計判断**である（研究所／図鑑／譲渡局の3チャネルを独立させる総則の方針に基づき、図鑑サイトから研究所への回遊導線をあえて作らない）。

Astro移行の際、この非対称性を「実装漏れ」と誤認してWORLD nav・フッター等に`land.html`へのリンクを追加してしまわないこと。現状維持が正しい仕様である。

### 11-1. `land.html`の扱い（確定：ファイル名を`labo.html`に変更、10章のドメイン構成を見越す）

`land.html`は図鑑サイト内から一切リンクされていない独立ページ（Instagramプロフィール欄からの流入専用）のため、Astroの`src/pages/`でコンポーネント化する必要はない。**`public/`フォルダへの静的ファイルとしてそのままコピーする**方式で温存する。

その際、ファイル名を`land.html`から**`labo.html`に変更する**。10章で検討中の将来のドメイン構成（`pelicanworks.site/labo`）を見越した命名であり、今回のAstro移行のタイミングで先に揃えておく。

ただし、既存の`land.html`というURLは、Instagramプロフィール欄・過去投稿に**すでに埋め込まれている可能性がある**。ファイル名変更に伴い、`_redirects`に以下を追加し、旧URLへのアクセスを保護すること（9-3のリダイレクト方針と同様）。

```
/land.html  /labo.html  301
```

なお、Instagramプロフィール欄のリンクを実際に新URL（`labo.html`）へ張り替える作業は、コード側の対応とは別に、**ボス側で行う必要がある**（この要件書の対象外）。
